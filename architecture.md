## Objective

Build a reproducible, defensible ML assignment in this folder from data contract to final business recommendation. The primary branch is binary classification for credit-risk screening. The model may prioritize enhanced human review; it must not make an automatic lending decision.

The South German Credit dataset is a historical proxy: its target is `credit_risk` (`bad`/`good`), not a directly observed “default in the next 12 months” field. The notebook and presentation must state that limitation explicitly and keep the assignment’s business assumptions separate from observed data.

## Waves of construction and execution

### Wave 0 — scope, provenance and reproducibility

Deliver:

- confirm the exact assignment rubric and required output files;
- record dataset source, download date, SHA-256 and license;
- pin or record Python and package versions;
- create the folder structure above;
- write a run manifest and a reproducibility README;
- define the positive class as `bad/default-risk` before any model code.

Acceptance gate: another person can identify the data, target, source, environment and exact command sequence without conversation context.

### Wave 1 — data contract and exploratory audit

Deliver:

- load the raw UCI file without changing it;
- map technical names to readable names while retaining the original names;
- document quantitative, categorical and ordinal variables;
- check missingness, duplicates, impossible values, class balance and category levels;
- check for target leakage and variables unavailable at the prediction moment;
- produce an EDA table and limited business-relevant plots;
- document the proxy-target limitation and historical-data limitation.

Acceptance gate: schema tests pass, `bad` is the positive class, no target-derived field enters `X`, and every transformation is reproducible.

### Wave 2 — preprocessing pipeline and baselines

Deliver:

- freeze a stratified test set before model selection;
- use a preprocessing pipeline fit only on development folds;
- one-hot encode nominal variables;
- handle ordinal variables with a documented ordering or a conservative categorical treatment;
- scale only where the selected estimator needs it;
- create a majority-class baseline and a simple interpretable baseline;
- establish random seeds and deterministic output tables.

Recommended split: hold out a stratified 20% test set once. Use the remaining 80% for stratified cross-validation and out-of-fold probability generation. If the rubric requires three named partitions, expose a 64% train / 16% validation / 20% test view, while keeping all preprocessing and tuning inside the development data.

Acceptance gate: the test set is untouched by feature fitting, threshold tuning, model selection and plots used for decisions.

### Wave 3 — candidate model construction

Build and compare:

1. majority baseline;
2. Logistic Regression as the interpretable probability baseline;
3. Decision Tree with controlled depth as an interpretable non-linear comparison;
4. Random Forest as the stronger ensemble comparison.

Optional models are allowed only if they answer a business question and do not distract from the required comparison. Every candidate receives the same split logic, preprocessing discipline and evaluation protocol.

Acceptance gate: select the candidate using development/CV evidence, not the frozen test set. Record model parameters, package versions, seed and rationale.

### Wave 4 — classification testing sequence

This is the mandatory model-testing order.

#### 4.1 Data and probability integrity

- verify class labels and positive-class direction;
- verify predicted probabilities correspond to the positive class;
- verify no preprocessing leakage;
- verify fold-level class balance;
- compare against the majority baseline;
- check probability calibration before treating a score as a probability.

#### 4.2 Discrimination without choosing a policy

On development out-of-fold predictions, report:

- ROC-AUC;
- PR-AUC / average precision;
- log loss where probabilities are available;
- calibration curve and Brier-style probability check where appropriate;
- cross-validation mean and dispersion.

These scores compare ranking and probability quality. They do not choose the operating threshold.

#### 4.3 Threshold table

For every candidate threshold, calculate:

- confusion matrix: TP, FP, TN, FN;
- precision;
- recall/sensitivity;
- F1 as the third combined classification metric;
- specificity;
- number and percentage sent to review;
- expected defaults prevented;
- gross loss avoided;
- review cost;
- lost contribution from unnecessary review;
- net screening value;
- cost per expected default prevented;
- missed avoidable loss.

Use at least six operating points:

1. `0.50`, only if the probability scale makes it meaningful;
2. low threshold / high-recall point;
3. high threshold / high-precision point;
4. capacity-constrained point: top 20% or at most 1,600 of 8,000 monthly applications;
5. best development net-value point;
6. recommended point after reviewing value, risk, capacity and friction.

The threshold is not itself a quality metric. It is the policy lever that changes precision, recall, workload and economics. Precision and recall must always be reported at the selected threshold, not only globally.

#### 4.4 Frozen test confirmation

After model and threshold are frozen, evaluate once on the untouched test set. Report the same classification metrics and business KPIs. Do not change the threshold after seeing test performance; if it fails, record the failure and return to development data.

#### 4.5 Robustness and governance

- repeat development evaluation across seeds or folds;
- inspect subgroup error rates where variables permit a responsible analysis;
- inspect calibration drift risk;
- test capacity shortfall and excess-demand scenarios;
- document that the model prioritizes manual review, not approve/reject decisions;
- list monitoring triggers and human override rules.

### Wave 5 — threshold policy and business recommendation

Deliver:

- a final operating-point table;
- a one-paragraph policy in plain language;
- review workflow: who reviews, what evidence they see, what outcomes are recorded;
- sensitivity analysis for review effectiveness, LGD, review cost and abandonment;
- limitations and pre-rollout tests;
- recommendation of threshold versus top-k ranking versus segmented policy.

The recommended policy must answer: what happens to a flagged application, what happens to an unflagged application, what happens when the review queue exceeds capacity, and how performance will be monitored after launch.

### Wave 6 — regression branch and R²

R² belongs here only if a separate continuous target is required. It is not a valid replacement for precision, recall or threshold testing in the binary Credit Risk classifier.

For a genuine regression target:

1. define the continuous target and prediction moment;
2. create a mean-prediction baseline;
3. use the same leakage-safe pipeline discipline;
4. evaluate MAE, MSE/RMSE and R²;
5. inspect residuals and large-error cases;
6. use cross-validation on development data;
7. freeze the final model and confirm once on test;
8. translate error size into business consequences.

R² can be negative and is not comparable across unrelated datasets without context. It must be accompanied by MAE/RMSE and a business interpretation.

### Wave 7 — notebook, report, slides and AI manual

Deliver in assignment order:

- end-to-end notebook with framing, data audit, preprocessing, models, metrics, threshold table, sensitivity and recommendation;
- 8–10 slide business deck plus up to 4 appendix slides;
- 2–4 page GenAI-use manual with tools, workflow, five pivotal interactions, two failure cases, understanding check and authorship statement;
- model card and reproducibility README;
- final testing report with exact evidence paths.

No result enters the deck unless it is traceable to a saved table, figure or test artifact.

### Wave 8 — zero-context sub-agent review

Use independent reviewers with no access to this conversation, previous reviewer comments or hidden reasoning. Each reviewer receives only the relevant artifact bundle, the assignment rubric and a short task prompt.

Reviewer A — data and leakage:

- verify target direction, prediction moment, missingness, leakage, split and preprocessing;
- report `PASS`, `PASS WITH FINDINGS` or `FAIL` with evidence.

Reviewer B — metrics and threshold:

- recompute or independently inspect precision, recall, F1, confusion counts and threshold table;
- check that capacity and economic formulas are correct;
- verify no test-set tuning.

Reviewer C — code and reproducibility:

- run only the approved safe test command;
- inspect relative paths, seeds, package versions, notebook restartability and output determinism;
- report exact failing file/cell/line.

Reviewer D — business and rubric:

- assess whether the recommendation follows from the evidence;
- check that model quality and business reasoning receive equal attention;
- detect unsupported claims, missing limitations and automatic-decision language.

Reviewer E — adversarial/red-team review:

- search for target leakage, prevalence mistakes, threshold cherry-picking, misleading plots, unfair proxy interpretation and unsupported causal claims;
- attempt to falsify the recommendation using the saved evidence.

Each review must produce a structured report with: verdict, severity (`blocker`, `major`, `minor`), evidence path, explanation, and proposed fix. Reviewers do not edit the implementation. Their reports are merged only after all independent reviews are complete.

### Wave 9 — repair, re-test and final acceptance

- triage all findings;
- repair blockers and majors;
- rerun the focused tests affected by each repair;
- rerun the complete acceptance suite;
- ask at least one independent reviewer to re-check every repaired blocker/major;
- freeze the final model, threshold and artifacts;
- write the final handoff and rollback instructions.

Done means: clean restart works, tests pass, the frozen test result is recorded, the business recommendation is reproducible, all reviewer blockers are closed, and the notebook/deck/manual agree with one another.

## Independent testing sequence summary

```text
schema/target → leakage/split → baseline → CV model comparison
→ out-of-fold probabilities → ROC-AUC/PR-AUC/calibration
→ threshold sweep → precision/recall/F1 + confusion matrix
→ capacity/economic policy → freeze model + threshold
→ one untouched-test confirmation → subgroup/robustness review
→ zero-context reviewers → repair → independent re-test
```

For regression, use a separate branch:

```text
continuous target → mean baseline → CV
→ MAE/RMSE/R² → residual/error analysis
→ freeze model → one untouched-test confirmation
```

## Safety and rollback

- Original course/download files are read-only inputs.
- Every generated result is under this assignment folder.
- No secrets or `.env` files are read.
- The raw data copy, run manifest and final artifacts are retained.
- A bad model or threshold is rolled back by selecting the previous frozen manifest/model artifact; no raw data is deleted.
- No external publication, deployment or automatic lending decision is in scope.
